# V1 GAP REGISTER

Produced 2026-09-01 by a 186-agent analysis of the two contracts against the implementation.
Every gap below was found by one agent and then **adversarially verified by a second**, prompted to
refute it and defaulting to refuted when uncertain. 118 survived. Gaps the verifier refuted, or
judged not actually required by the contract for V1, are not listed.

This document exists because the phase history reads as though the product is nearly finished and
it is not. The engine, the rules, the twin, the traceability chain and the change model are real,
well-tested libraries. What is largely missing is the product on top of them: the lifecycle never
transitions, no evidence or approval is ever recorded, no audit event is ever written, and there is
no sign-in. Those are not polish items — they are the difference between a platform and a demo.

Four defects that were **not** in the register, each found by running something rather than reading it:

- **Every icon on all 50 screens rendered as its own name.** There was no font. The header brand mark
  read `settings_suggest`. Icons are `aria-hidden`, so axe stepped over them, and the E2E suites
  address the product by role and text — which stayed correct.
- **Signing in emptied the product.** The tenant resolver read only the guest cookie, so a signed-in
  caller resolved to no tenant and row-level security returned nothing.
- **The evidence page became a wall.** Making the rule criteria satisfiable took it from 17 forms to
  64 — 504 controls, 731 KB, measured — and Firefox's accessibility-tree walker overflowed its stack
  on it.
- **Then the traceability page became the same wall**, for the same reason and one closure later.
  Materialising the emitted requirements took it to 3,239 elements and 1.28 MB — 553 list items in
  "Every chain" alone, and 117 non-blocking gap cards carrying three distinct sentences between them.
  Firefox took longer than the test timeout building an aria snapshot of it, so the accessibility
  check *timed out* rather than failing, which is a much harder failure to read. The chains moved to
  a page each: 572 elements, 269 KB, and a drift guard that fails if they come back.

## Domain summaries

### outbox — 2 gap(s)

The contract does make the outbox a V1 element — plan §3 "Eventing" lists "transactional outbox" and "internal domain events" under V1 (MASTER_IMPLEMENTATION_PLAN.md:363-368) and §5 lists OutboxEvent as entity 56 (:560) — and gap-spec §47 requires material domain changes *that need asynchronous side effects* to write entries inside the same DB transaction. The mechanism is genuinely built and verified: table with RLS, cron drainer using FOR UPDATE SKIP LOCKED with claim expiry, queue consumer, dead-lettering, and a separate pure model in packages/resilience. KI-059 is confirmed exactly as written — the only INSERT into outbox_events in the whole repository is in a test — but the producers are **not** independently required for V1, because four of the five transitions §47 names (gate changed, approval granted, change request applied, deployment recorded) are not persisted anywhere at all, the fifth (project version created) never increments projects.version, and V1 has no asynchronous transport (§43 defers email/slack, §44 makes every integration PLANNED). The real gaps are that KI-059 misdescribes the work that remains, that no request-path write runs in a transaction so §47's mechanism has no attachment point, and that two divergent outbox designs coexist where the fully-tested one is the unused one.

### evidence-storage — 8 gap(s)

Both contracts require evidence as stored artefacts, not just references: plan §3.2 mandates S3-compatible object storage with signed access and recorded hashes, §23 lists an `EvidenceUploader` component, §24 locks screen 44 "Evidence", §32.10 enumerates "evidence upload" as Playwright critical journey 18, and gap-spec §35 is a twelve-item "Required:" list of upload controls (randomised key, no user-controlled path, signed download URLs, content-disposition safety, tenant ownership). Nothing in the contract defers any of this — plan §36's defer list omits it entirely, and gap-spec §85.15 makes "maintain living documents/evidence" a V1 success criterion. What exists is the model only: `packages/governance/src/evidence.ts` implements §32's record shape and three of §35's twelve checks as pure functions with no caller outside tests, and the R2 `EVIDENCE` binding at `apps/web/wrangler.toml:100-102` has no reader or writer (KI-061 confirmed exactly as claimed). The deeper finding is upstream of storage: no code path anywhere creates an EVIDENCE or APPROVAL twin node, so all 17 MANUAL gate criteria in `packages/rules/src/gates.ts` — 16 of them blocking, spanning Architecture, Planning, Development, Security, Release Readiness, Production Verification, Operations and Handover — are permanently unsatisfiable, and no known issue records that consequence.

### queues — 7 gap(s)

The contract mandates surprisingly little scheduled work for V1: gap-spec §46 (job failure semantics), §47 (transactional outbox, "worker processes outbox idempotently") and §48 (idempotency) govern *how* async work must behave, but the only clock-driven job V1 genuinely requires is guest-project expiry (§5.3 "guest projects expire automatically", §5.2 "Do not store full sensitive project data permanently without signup") plus §68's post-live operational checks. Recalculation is event-driven (§27, plan §32.6 — triggered on change apply, never on a timer), and notifications (§43) have no transport, no persistence and no DB table in V1, so neither needs a scheduler. What exists is the inverse: a fully provisioned Cron + Queues + DLQ outbox pipeline (apps/worker/src/index.ts, 350 lines) whose producers do not exist (KI-059) and whose five handlers are logging no-ops, running once a minute against an empty table — while `purgeExpiredGuestSessions` is written, unit-tested, and never invoked by anything. The Queues hop itself is not mandated by §47; a single cron would satisfy the contract's letter, and the cron that is deployed is doing the one job V1 does not yet need and none of the job it does.

### auth-oidc — 12 gap(s)

The contracts require a provider-neutral OIDC identity keyed on (issuer, subject) (gap-spec §6.1), "at minimum one production login method" (§6.2), eight defined session controls (§6.3), atomic guest-to-account conversion (§5.4, §88), and post-live verification of "signup/login" plus a "critical authenticated journey" (§67) — and the plan names login, signup-to-save, logout/session-expiry, organization users and permission-denied as required Playwright journeys (§32.10). What exists is the two ends and nothing in between: a genuinely provider-neutral `resolveIdentity` that takes already-verified claims (packages/db/src/identity.ts), a deny-by-default RBAC matrix and an ordered authorisation middleware (packages/db/src/rbac.ts, authorize.ts), and a complete, well-tested guest session lifecycle including an idempotent `convertGuestSession` — all of which have zero callers in apps/web outside tests. There is no authorization-request builder, no callback route, no state/nonce/PKCE, no token validation, no session store or authenticated cookie, no logout, no save/signup surface, and — contrary to docs/DEPLOYMENT_RUNBOOK.md:295 — no local mock provider; meanwhile docs/THREAT_MODEL.md cites tests in a `packages/auth` that does not exist, and an expired guest cookie is still honoured because every route trusts the raw cookie value without re-reading `guest_sessions.expires_at`. Everything listed can be built and fully tested against a locally-run mock issuer — the authorization request, PKCE/state/nonce, the callback, ID-token validation against a JWKS, the session table and signed cookie, guest conversion, org bootstrap, logout, CSRF and the E2E journeys; exactly one step genuinely requires an external provider account: registering the redirect URI to obtain a real `client_id`/`client_secret` and pointing the issuer discovery URL at it as deploy secrets.

### ui-states — 3 gap(s)

Plan §23 (lines 1280-1283) names EmptyState, LoadingState, ErrorState and PermissionState as core primitives; §24 (lines 1399-1415) makes empty/loading/error/blocked/no-permission required reusable states; §4.2 (lines 445-448) requires per-screen empty/loading/error/permission status in DESIGN_SCREEN_MAP.md; gap-spec §55 (line 2062) requires the UI to map error codes to safe messages. What exists: `EmptyState` (4 variants) and `Modal` were built in Phase 2 closing the first half of KI-008, `Button` carries a `loading` prop, and the status vocabulary (GATE/HEALTH/VALIDATION incl. BLOCKED, EXCEPTION, UNKNOWN) is complete and non-colour-encoded. What does not exist: across the entire 19-route `apps/web/src/app` tree there are **zero** `loading.tsx`, **zero** `error.tsx`/`global-error.tsx`, **zero** `not-found.tsx`, zero `Suspense` boundaries, zero `try/catch` in any page, and zero `aria-busy` in any route — so the loading, error and permission-denied surfaces are Next.js stock pages, not this design system. `LoadingState`, `ErrorState` and `PermissionState` were never built; `EmptyState` is imported by exactly one route (the fabricated `/p/[projectId]`), while all nine real data routes hand-roll their own empty markup. KI-008's second sentence — "Every screen also needs empty/loading/error/permission states that were never drawn" — remains open and untracked, and DESIGN_SCREEN_MAP.md's state columns record `—` for Loading on every one of its 64 rows.

### responsive-a11y — 9 gap(s)

The responsive contract is real and unusually well-built: gap-spec §3.3's six breakpoints and §3.4's ten dense representations are a typed source of truth (packages/design/src/responsive.ts) generated into docs/RESPONSIVE_CONTRACT.md with a CI --check, and 18 of 19 routes carry an axe assertion — better a11y coverage than most shipped products. The gaps are not in what was decided but in what verifies it: every §3.4 assertion is either prose-against-prose (packages/design/test/responsive.test.ts) or gated behind `isMobile`, so the contract's own central claim — "the accessible alternative is always in the document, at every size" — is checked at exactly one size; the structural a11y suite (skip link, landmarks, heading order, keyboard reachability, 320px reflow) runs only against /p/proj_demo, a Phase-2 skeleton that renders literals; and the whole mobile suite skips WebKit by browser name, so iOS Safari has never run it, including against HTTPS staging where KI-024 made that a mandatory gate. Separately, Phase 16's task list (locked screens 59–64) and plan §32.10's critical journeys 37 and 38 were never built, while the phase is recorded as met on its gate line alone. KI-005's contrast test does exist (apps/web/test/design/contrast.test.ts) and covers four of its five named tokens.

### security-controls — 7 gap(s)

The contract requires a broad set of security controls: plan §18 (CSP, secure headers, tenant isolation, object-level authorization, least privilege, rate limiting, file-upload validation, no secrets in logs, secret/dependency scanning, SAST, immutable audit trail), gap-spec §7.5 (every tenant-owned query must require tenant context), §34–§36 (threat model, upload security, rate limits), §40 (audit immutability), §54 (automated tests proving sensitive values are not logged), §65 (pre-live attack suite) and §66 (mandatory pre-live gate). Four controls are genuinely strong and test-enforced: CSP and security headers (`e2e/security-headers.spec.ts`), log redaction (`packages/shared/test/logging.test.ts`), 404-not-403 BOLA/IDOR behaviour on a self-discovering route suite (`e2e/isolation.spec.ts`), and the RLS/least-privilege-role mechanism itself (`packages/db/test/tenant-scope.test.ts` plus the pooled gate `scripts/verify-pooled-isolation.mjs`). The gaps are concentrated in controls that exist as code or as documentation but are never reached by a request: `withTenant`/`applyTenantScope` has zero callers so RLS and the `govintel_app` role apply to nothing the deployed app serves, nothing ever inserts into `audit_events`, `checkUpload` is called only from its own unit test, and rate limiting is an in-isolate `Map` with no test while the edge replacement the architecture document names does not exist in any configuration. SAST is required by both plan §18 and gap-spec §66 and is absent entirely, and the generated threat model asserts mitigations and verifications (signed cookies, per-address rate limits, a `packages/auth` test suite) that do not exist.

### privacy-retention — 9 gap(s)

The contracts require a privacy-first platform with data minimisation, configurable retention, export, deletion, an explicit external-AI boundary (plan §19:1111-1130), four named documents (plan §0.5:150,157; gap-spec §37:1681, §38:1714), automatic guest-project expiry (gap-spec §5.3:372-374), V1 project export (gap-spec §39:1739), and a documented legal-deletion strategy for audit data (gap-spec §40:1767). What exists is the *analytical* half and almost none of the *operational* half: retention classes (packages/governance/src/evidence.ts:64-105), a correct archive retention refusal (packages/completion/src/archive.ts:163-180), a strong external-AI copy-safety screen (apps/web/src/app/intake/[projectId]/prompt/page.tsx:120-185), and centrally-enforced log redaction (packages/shared/src/logging.ts) are all implemented and tested. But every path that would actually delete, expire, export or archive data is either absent or has no caller: `purgeExpiredGuestSessions` (packages/db/src/guest.ts:172) is referenced only by tests, `mayDelete` (evidence.ts:324) only by tests, `checkArchive` only by tests, `projects.archived_at` is read but never written, there is no export route or module, and there is no delete path of any kind. The net effect is that anonymous visitors' free-text project descriptions are stored permanently with no expiry, no deletion, and no export — the exact outcome gap-spec §5.2:366 forbids.

### lifecycle-approvals — 13 gap(s)

Plan §6 mandates a 12-state, centrally-validated lifecycle; gap-spec §33 mandates an approval object separate from completion; plan §24 locks screens 28 (Quality Gates), 35 (Change Request Center), 46 (Approvals & Sign-offs), 47 (Retrospective) and 48 (Completion & Handover); gap-spec §85 requires a user to be able to "manage changes" and "complete/handover the project". The domain layer for all of this is built and well-tested — `packages/rules/src/lifecycle.ts`, `packages/governance/src/approval.ts`, `packages/completion/*`, `packages/change/src/request.ts` — but essentially none of it is wired to the product. Only four mutating server actions exist in the whole app (startProject, answerQuestion, submitImport/acceptImport/rejectImport, generatePlan); `projects.lifecycle_state` is never written, so every project is permanently `IDEA`; no `approvals` table exists; nothing ever creates an APPROVAL or EVIDENCE twin node, which makes 8 of the 11 gates arithmetically unpassable and stops the state machine at PLANNING even if a transition UI existed. The user-reachable flow is create → intake → import → generate plan → eight read-only analysis pages. Approve, close, archive and change-request are unreachable by any route.

### rules-calculations — 12 gap(s)

The rule catalogue itself is in excellent shape: 287 rules across all 14 gap-spec §14 categories (every floor met, `checkCatalogue()` returns zero problems), every rule's intake keys resolve to real fields, and I verified by exhaustive search that all 287 can reach APPLIED under some project type / lifecycle / methodology / intake combination. The calculation engines (money in minor units, three-point estimates, contingency sizing, feasibility §22, health §23) are well built, versioned and genuinely explanation-first. The gap is almost entirely in the wiring: the evaluator produces six kinds of emission and the product consumes only two — 73 rule-emitted gate criteria, 139 emitted requirements, emitted risks and all 8 declared `calculationEffects` are computed and discarded, while a second, hardcoded rule set inside the twin generator produces the requirements and risks the UI actually shows. Downstream, the resource/capacity engine is called with `resources: []` at every call site, the budget engine's cost-line half is never reachable from the UI, the methodology engine is bypassed by a hardcoded `'AGILE'`, and the `twin_calculations` snapshot table is created but never written.

### traceability-impact — 6 gap(s)

The contract requires a walkable Requirement → Architecture → Work → Implementation → Test → Evidence → Release chain with missing-link detection in both directions (plan §10, Phase 10 gate "complete Requirement→Release chain verified"), and per-relationship impact propagation with the ten-step change-request sequence (gap-spec §27, §27.1, §28). The engines are genuinely strong: `packages/twin` implements all 32 node classes and all 17 edge classes of gap-spec §8.1/§8.2, every chain triple is legal under `EDGE_LEGALITY`, `packages/traceability` walks the chain in both directions with three link statuses, and `packages/change` implements deny-by-default propagation, path-carrying impact reports and the §28 concurrency check. The wiring is where it fails. I ran `analyse()` against the graph `generateProject` actually persists and against that graph plus the decomposition: in the first case every requirement breaks at WORK, in the second every requirement breaks at TEST, and EVIDENCE is MISSING in both — so "Fully traced" is 0 for every real project, the Phase-10 gate is verified only against hand-built unit fixtures, and the change surface is a preview with no request, approval or apply path behind it.

### operations — 6 gap(s)

The contract requires four things of operations: recovery targets defined, drilled and explicitly accepted before production (gap-spec §51); a read-only/degraded posture that never reports a mutation it did not apply (§52); a Release Readiness Gate over eight named artefacts (§15.8); and a Production Verification Gate over ten named checks (§15.9). The engines are genuinely built and are the best part of this domain — `packages/release/src/deployment.ts` models all ten §15.9 checks with `NOT_CHECKED ≠ PASSED` semantics, `packages/resilience/src/degraded.ts` models §52 exactly, and `/api/health` reports version and commit from the running process and returns 503 rather than a 200 with a false field. What is missing is everything on either side of those engines: no user or operator can record a single production check, release plan, ownership, incident or debt item — the two pages that would show them hard-code every input to `[]`, no code path anywhere creates an EVIDENCE or APPROVAL node, so every MANUAL gate criterion is permanently unsatisfiable; the §15 gate catalogue publishes 5 of the ten §15.9 criteria as if complete; no restore, secrets-restoration or object-storage recovery test has ever been run, leaving §51 unmet for production; and the runbook that an operator would open during an incident misstates the deployed state in three places.

### product-naming — 2 gap(s)

Neither contract names the product: `grep -c -i govintel` returns 0 for both MASTER_IMPLEMENTATION_PLAN.md and IMPLEMENTATION_GAP_CLOSURE_SPEC.md, and neither contains "itisyou". The rename to "build.itisyou" is therefore an owner decision that supersedes a repo document of record (docs/DESIGN_SCREEN_MAP.md:209 declares "GovIntel Platform" canonical, and KI-010 points at it), not a contract requirement in itself. What the contracts do mandate, and what makes the rename load-bearing, is production verification of "correct application identity" (plan §28, line 1518) and "correct hostname" / "page identity" (gap-spec §67, lines 2328 and 2330). The user-facing surface is remarkably small and cleanly separated from internals: exactly 7 literal display strings in 5 shipped files, against 678 total `govintel` occurrences across 186 files that are all internal identifiers (`@govintel/*` package scope, `govintel_app` DB role, `govintel_guest` cookie, `govintel-*` Cloudflare resources, `govintel_test` CI database) and must not be touched.

### deadcode-deps — 7 gap(s)

The contracts govern this domain through plan §38 ("never introduce major infrastructure without evidence it is needed"), gap-spec §66 (pre-live dependency scan), and the project's own precedent in KI-020, where `drizzle-kit` was deleted purely for being declared and unused. Against that bar the repository carries three distinct problems. First and worst: `@electric-sql/pglite` — a 20 MB embedded WASM Postgres that ADR-0002 scopes to dev and test — is statically imported from `apps/web/src/lib/server/database.ts:3` and from `packages/db/src/client.ts:18`, so it is in the deployed Cloudflare Worker's module graph; Next's own file trace for `/api/health` lists 176 PGlite files totalling 20.08 MB against 2.24 MB for everything else, `docs/CLOUDFLARE_DEPLOYMENT_ARCHITECTURE.md:63` asserts "PGlite never ships", and the runtime guard that is supposed to make this safe is fail-open. Second: roughly 5,000 lines across 17 `packages/*` modules — the entire RBAC/authorisation stack, all of `packages/discovery`, three of five `packages/governance` modules — are reachable only from their own unit tests, so the engines exist and the application cannot call them. Third: four declared dependencies (`zod`, `postgres` in apps/web; `@neon/env`, and misplaced `@neon/config`/`postgres` at root) are never imported.

### external-ai — 9 gap(s)

The contract requires external AI to be optional, provider-neutral, copy-paste only (plan §2.2), with sensitive-data redaction before the prompt is copied, a "what leaves the platform" screen, and an organisation policy able to switch the workflow off (plan §19, gap-spec §11.3). The core machinery is genuinely built and genuinely provider-neutral: `packages/interchange` has a real detector-based redaction path, a fourteen-layer import validator matching gap-spec §12.1 layer for layer, four separate version identifiers per plan §11, and 121 unit tests across `validate.test.ts` and `staging.test.ts` — and there is no paid AI SDK, no AI binding and no outbound AI call anywhere in the tree. What is missing is the *policy* half. `EXTERNAL_AI_MODE` is consulted at exactly one call site (the prompt page); the import half of the workflow is ungated, the per-tenant `organizations.external_ai_mode` column is never read, `APPROVED_PROVIDERS_ONLY` has no behaviour at all, the project name escapes the redaction pass entirely, and an accepted import never reaches the project model, so plan §2.2 step 12 never happens.

### performance — 6 gap(s)

The contracts declare four numeric performance targets (plan §33:1806-1809), make "performance acceptance" a hard Release Candidate requirement (gap-spec §78:2558) whose gate Phase 18 declared passed, require a "performance summary" in the final evidence pack (gap-spec §79:2583), and mandate small/medium/large fixtures (gap-spec §63:2192-2223). What exists is one latency assertion in the whole repository — `BUDGET_MS = 10_000` at e2e/staging.spec.ts:91 — which is 25x looser than the tightest declared target, plus no LCP measurement, no defined test load, no p95 computation, no request-duration telemetry, and none of the §63 fixtures. I measured the Phase-19 connection-per-operation change directly against staging and it is not the N+1 the brief hypothesised: one full connection lifecycle behind Hyperdrive costs roughly 1ms at the median (/portfolio, 0 connections, median 83ms vs /api/health, 1 lifecycle, median 84ms over 15 samples each), and the tail under 20-way concurrency is isolate cold start, present identically on the zero-connection route. The genuine unquantified exposure is elsewhere: the full deterministic engine re-runs on every render of four pages with no caching, no persistence and no row caps.
